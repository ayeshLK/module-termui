A Ballerina program cannot wait for "a key or a timer or a message" at once, so the runtime wakes to
look. How often it wakes is the idle cost.

## Adaptive backoff

<BackoffChart />

- It starts at `pollInterval` (5 ms).
- After every 20 checks that found nothing, the sleep doubles.
- It stops at `maxPollInterval` (0.5 s), which it reaches after about 13 seconds of idleness.
- A key, an effect result or any message the program sent returns it to `pollInterval` at once.

The result, measured on the counter example: a waiting program uses about 1% of a CPU core instead of
about 10%.

## The trade-off

**The first key after a long pause waits for the current sleep to end**, in two hops: the terminal's
input check, then the runtime loop. On the counter example the median first key takes:

| Idle before the key | Median wait for the first key |
|---|---|
| 1 second | about 40 ms |
| 3 seconds | about 110 ms |
| more than 13 seconds | about half a second |

These are magnitudes from a developer laptop, not guarantees. Lower `maxPollInterval` for a snappier
first key, at the price of more idle CPU. Set it at or below `pollInterval` to turn the backoff off.
`Interface` takes a `maxPollInterval` argument and passes it to the terminal too. The default is frozen
for the whole major version.

## Timers

- The ticks of a timer started with `every` do not end the backoff.
- The ceiling is lowered to half the period of the program's fastest timer, so ticks are handled on time.
- A tick that leaves the view unchanged does not redraw.

A program with a 100 ms timer therefore idles at a few percent, mostly the work of its own `update` and
`view` ten times a second. If you animate, keep `view` cheap.

## Measuring your own program

The repository has two scripts that run a built program on a pseudo-terminal:

- `bench/idle_cpu.py` reports the CPU time, memory and bytes written by a program that is only waiting
  for a key. A program with no fast timer should use a few percent of one core at most and write nothing.
- `bench/latency.py` reports the time from a key press to the first byte of output after idle gaps of
  different lengths.

Timing on a laptop or a shared runner is noisy, so use them to look at numbers before a release, not to
gate a build. The commands are in
[`bench/README.md`](https://github.com/ayeshLK/module-termui/blob/main/bench/README.md).
