A termui program is a class with two methods. Everything else in the library exists to feed them
messages and to draw what they return.

<InteractiveLoop />

- **`update(message)`** is called once for each message. It changes the program's state and may return
  a **command**: what to do next (`quit()`, start an effect, commit some finished output).
- **`view()`** returns the live region as lines of styled text. It has no side effects and returns the
  whole region each time.
- A **message** is a key press, a resize, a timer tick, or the result of an effect. They all arrive in
  one queue, so `update` never runs twice at the same time.

The runtime applies every message that is waiting, then calls `view` once and draws **one frame**,
writing only the cells that changed. Ten key presses that arrive together cost one frame, not ten.

`*termui:Program` says the class is a program. Its state, `count`, is an ordinary field. Only
`update` changes it, because only `update` runs on the program's strand.

`update` receives every message. A key press is a `term:KeyEvent`, so the program checks the type
first and ignores anything else by returning `()`. Returning `termui:quit()` ends the program.

`view` returns lines, and each line is a list of styled spans. Nothing here talks to the terminal.
The runtime decides what has to be redrawn.

## Why it is shaped like this

- **One strand for state.** Because every message goes through the queue, you never lock your state.
  Work that takes time runs as an **effect** on its own strand and reports back with a message; see
  [commands and timers](../commands-and-timers/).
- **One frame per batch.** A fast producer, such as streamed text, cannot make the terminal flicker
  or fall behind: the renderer draws the latest state, once.
- **`view` is a function of state.** That is what lets the same program run in a pipe or under test:
  only the renderer changes.
