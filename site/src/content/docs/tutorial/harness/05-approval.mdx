An agent that runs tools should ask first. In this step the scripted model finishes its answer and then
asks to run one tool, `Bash(bal test)`. The effect waits for your yes or no before it runs anything.

<CastPlayer cast="step5-approval.cast" caption="Step 5: a tool call approved with y, and a second one denied with n." />

## What changed

Starting from step 4, you:

- add `ToolStarted` and `ToolFinished` messages and a `runTool` function that asks before it runs,
- commit a finished tool call as a small block: a green or red dot, the tool, and its result,
- show "Waiting for approval" in the status line while the question is up, and
- decide what the program does when there is nobody to ask.

## The program

Start from step 4's complete program, which is on [step 4](../04-status/), with its `main.bal` and
`model.bal`. You add the tool call in four stages, and `bal build` compiles after each one. Each stage
says whether its code replaces something you already have or is added to it, and which file it is in.

### 1. The tool messages

In `model.bal`, add these two message types after `Token`:

```ballerina
type ToolStarted record {|
    "toolStarted" kind = "toolStarted";
    int turn;
    string name;
    string arg;
|};

type ToolFinished record {|
    "toolFinished" kind = "toolFinished";
    int turn;
    string name;
    string arg;
    string summary;
    boolean ok;
|};
```

### 2. Asking from an effect

The model has to ask before it runs a tool. In `model.bal`, add the tool's name and argument after
`chunks`:

```ballerina
const string TOOL = "Bash";
const string TOOL_ARG = "bal test";
```

Add `runTool` after `streamAnswer`:

```ballerina
// Asks before running the tool. `confirm` waits for the user's answer, and with no terminal to answer it
// returns the default we pass (false: deny) at once, so a script never hangs and never runs a tool nobody
// approved.
isolated function runTool(termui:Session session, int turn, decimal delay) returns error? {
    session.send({kind: "status", turn, text: "Waiting for approval"});
    boolean allowed = check session.confirm(string `Allow ${TOOL}(${TOOL_ARG})?`, false);
    if !allowed {
        session.send({kind: "toolFinished", turn, name: TOOL, arg: TOOL_ARG, summary: "denied by user", ok: false});
        return;
    }
    session.send({kind: "toolStarted", turn, name: TOOL, arg: TOOL_ARG});
    runtime:sleep(delay * 30);
    session.send({kind: "toolFinished", turn, name: TOOL, arg: TOOL_ARG, summary: "12 passed, 0 failed", ok: true});
}
```

`session.confirm(question, defaultAnswer)` shows the question below the live region and **waits** for the
answer. That is why it lives in the effect: waiting for a person would freeze the interface if the
program's own strand did it. While the question is shown, your key presses answer it instead of reaching the
program: `y` to allow, `n` to deny, Enter for the default, Esc for no.

The default is the part to think about. Here it is `false`: if there is nothing to answer, **deny**.

Replace `streamAnswer` so that it runs the tool when the answer was not interrupted:

```ballerina
isolated function streamAnswer(int turn, string question, decimal delay, CancelFlag flag) returns termui:EffectFunction {
    return isolated function(termui:Session session) returns error? {
        session.send({kind: "status", turn, text: "Thinking"});
        runtime:sleep(delay * 40);
        session.send({kind: "status", turn, text: "Responding"});
        boolean interrupted = false;
        foreach string piece in chunks(answerTo(question)) {
            if flag.isCancelled() || session.isStopped() {
                interrupted = true;
                break;
            }
            session.send({kind: "token", turn, text: piece});
            runtime:sleep(delay);
        }
        if !interrupted {
            check runTool(session, turn, delay);
        }
        session.send({kind: "done", turn, interrupted});
    };
}
```

Replace `answerTo` so the answer ends with a newline. Its last line is then committed before the question
appears:

```ballerina
isolated function answerTo(string question) returns string {
    return "You asked: " + question + "\n" +
        "This answer is streamed a few characters at a time.\n" +
        "Each finished line is committed to your scrollback, and the line being written stays live.\n";
}
```

#### When nobody can answer

`confirm` does not wait when there is no terminal to answer it. It returns the default you passed at
once, or a `NoTerminal` error if you gave none. `Interface` tells the runtime whether a user can answer,
as [modes and headless operation](../../../concepts/headless-modes/) explains. A script, a pipe or CI therefore
never hangs on a question, and, because the default is deny, never runs a tool that nobody approved. Decide
what "no answer" means for your program, and make it the safe thing.

### 3. Handling the tool messages

In `main.bal`, inside `update`, add these two branches after the one for `Status`:

```ballerina
        if message is ToolStarted && message.turn == self.turn {
            self.statusText = string `Running ${message.name}(${message.arg})`;
            return;
        }
        if message is ToolFinished && message.turn == self.turn {
            return self.onToolFinished(message);
        }
```

Add `onToolFinished` to `Chat`, after `ask`:

```ballerina
    private function onToolFinished(ToolFinished tool) returns termui:Command {
        text:Style markStyle = {fg: tool.ok ? "green" : "red"};
        return termui:commitBlock([
            [{text: "●", style: markStyle}, {text: " " + tool.name, style: {bold: true}}, {text: "(" + tool.arg + ")", style: {dim: true}}],
            [{text: "  ⎿  " + tool.summary, style: {dim: true}}]
        ]);
    }
```

The tool call is committed with `commitBlock`, like a finished line of the answer: it is written once
into your scrollback and never redrawn.

### 4. The status line while the question is up

Esc answers the question while it is shown, rather than interrupting, so the hint should say "answer
below" instead of "esc to interrupt". Inside `Chat`, replace `view` with this one:

```ballerina
    public function view() returns text:Span[][] {
        text:Span[][] lines = [];
        if self.partial != "" {
            lines.push([{text: self.partial}]);
        }
        if self.busy {
            string frame = SPINNER[self.ticks % SPINNER.length()];
            int seconds = (self.ticks - self.turnStartTick) / 10;
            // while a question is shown, keys answer it, so Esc is not "interrupt" then
            string hint = self.statusText == "Waiting for approval" ? "answer below" : "esc to interrupt";
            lines.push([
                {text: frame + " " + self.statusText + "… ", style: {fg: "brightCyan"}},
                {text: string `(${seconds}s · ${hint})`, style: {dim: true}}
            ]);
        }
        foreach text:Span[] row in self.editor.render(self.width, "❯ ") {
            lines.push(row);
        }
        return lines;
    }
```

## Check it without a terminal

A test has to answer the question, and that is trickier than it looks. If you push a `y` key before the
program runs, it reaches the program straight away, before the question exists, and ends up typed into the
prompt. The key has to arrive when a person's would: after the question is on the screen.

So the test uses a small terminal of its own. The `Terminal` type is a public interface, so a test can
wrap a `FakeTerminal` and hold one key back until the screen shows the question.

- Approving runs the tool, and denying does not.
- With `interactive: false`, which is what `Interface` sets when nobody can answer, the program never
  waits: the tool is denied and the transcript says so.
- Esc during the model's "thinking" stops the answer before any tool is asked for.

## Try this

- Run `bal run`, send a question, and answer `y`. Send another and answer `n`. The dot is green for the first
  and red for the second.
- Press Enter on the question without typing anything: that takes the default, which is to deny.
- Change the default in `runTool` to `true` and run the "no terminal" test. It now fails, because the tool
  runs unattended. That is the reason the default here is `false`.
